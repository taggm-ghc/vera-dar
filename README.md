# VERA-DAR

**Verifiable Evidence-based Research Answers**

VERA-DAR is an experimental research assistant that answers a question only from full-text documents it has checked, and shows which passage supports each sentence. When it cannot do that, it says so and gives a reading list of links instead of a guess. It was built during the AI engineering bootcamp capstone (TAI Labs Agentic AI Engineering Bootcamp, 2026).

## The problem

Language models write fluent research answers without showing how the evidence was found or read. A citation list does not prove the sources were examined, or that the answer follows from them.

VERA-DAR asks a narrower question: if the system acquires a full document, admits only the passages that bear on the question, and checks each answer sentence against the passage it cites, is the result easier to trust and to audit? Two things are needed: traceable evidence decisions, and an answer that is actually better. Neither substitutes for the other.

## How it works

```mermaid
flowchart TD
    UI["Streamlit UI<br/>streamlit_app.py, pages/"] -->|"X-API-Key"| API["FastAPI<br/>main.py: POST /ask"]
    API --> CAPS["Public-mode caps<br/>vera/public_mode.py"]
    CAPS --> SCOPE["Safety gate (no subject scope)<br/>vera/scope_router.py<br/>layer 1: rules, layer 2: LLM safety verdict"]
    SCOPE -->|"declined (unsafe)"| REFUSE["Fixed decline text"]
    SCOPE -->|"safe"| FD["Full-document path<br/>fulldoc_corpus, fulldoc_admission"]
    FD --> ADMIT{"admitted<br/>passages?"}
    ADMIT -->|"yes"| ANS["Answer from passages<br/>fulldoc_answer"]
    ANS --> CC["Claim check per sentence<br/>claim_check"]
    CC --> OUT["Cited answer<br/>(unsupported sentences removed)"]
    ADMIT -->|"no"| INL
    INL -->|"documents pass gates"| ANS
    INL -->|"none"| RL["Reading list with links<br/>search_providers: OpenAlex,<br/>DuckDuckGo lite (fallback)"]
    ADMIT -.->|"insufficient"| BG["Background acquisition<br/>auto_acquire"]
    BG --> STORE[("Postgres:<br/>full-text corpus")]
    FD --- STORE
    LLM["Groq models (provider chain)"] -.-> SCOPE
    LLM -.-> ANS
    LLM -.-> CC
```

What each step does:

1. **Safety check (before retrieval).** Layer 1 is a deterministic rule set (`config/scope_router.json`) that hard-blocks explicit personal advice, operational harm, prompt injection and coding tasks. Every other question goes to layer 2, a Groq model that returns a JSON safety verdict; only an exact `safe_request` verdict passes, and anything else (malformed, off-schema or unavailable) is declined. A declined question gets a fixed text, never model-written text. Subject matter is never a reason to decline and there is no fixed scope text: whether VERA-DAR's collection can answer is decided after retrieval, from the passages it finds (owner decision SCOPE-GATE-1104, 2026-11-04). The shipped config still has an off-topic reading-list path for layer-2 verdicts; its live behaviour after the gate change is offline-tested only.
2. **Full-document retrieval and admission.** Passages are retrieved from a small, operator-selected, licence-checked collection of full documents stored in Postgres. Each passage is evaluated and admitted or rejected with a reason code. No admitted passage means no generated answer. The model can also flag a false or ill-posed premise in the question, but only with a cited correction that passes the same claim check; an unverified premise flag counts as an evidence miss and starts acquisition.
3. **Answer and claim check.** The model writes from up to six admitted passages with numbered citations. A second model call judges each cited sentence against its passage. Unsupported sentences are removed, and if none survive, no answer is shown.
4. **Discovery and same-request acquisition.** *Superseded 2026-11-10: DuckDuckGo is a fallback only and arXiv is a portal; see the Update 2026-11-10 paragraph.* Discovery was DuckDuckGo first (used only as a pointer to scholarly identifiers), then OpenAlex, Europe PMC, DOAJ and arXiv, through a portal registry (`config/portal_registry.json`; the optional portal-use recorder is off by default). Acquisition runs inside the request when the collection has no answer or too little (a corpus miss or an insufficient result) or when the cited corpus content was added more than 24 hours ago (freshness check, `config/auto_acquire.json`). Full text comes from Europe PMC (JATS XML), or (*superseded 2026-11-10: the arXiv route is off*) from arXiv HTML only for a specific paper version whose own licence link is CC BY, BY-SA, BY-NC or BY-NC-SA, with the route evidence recorded. When the first search leaves fewer than six usable documents, further rounds use other query variants, up to six full texts per prompt; a round that finds fewer than six reports a resource limit, not an error, and the loop stops after two rounds with no new usable document (offline-tested only; six is an owner-declared target, not calibrated). A licence allowlist (`config/licence_allowlist.json`; Deny All: only listed licences are stored, ND and no-education-use licences are rejected) decides storage; documents without an allowlisted licence are not stored. A document is admitted only as full text: abstract-only records are never admitted. It must also pass the licence gate, content and injection checks and a per-document relevance gate. Documents with enough relevant passages are added to the collection. Optional lanes can add pages read for one answer only (see Search lanes below). Each request ends with a research outcome report saying what was tried, what was admitted and why candidates were not. A best-effort background job can follow; it lives in process memory and is lost on restart. Bounds are in `config/auto_acquire.json` (for example 120 jobs per hour (one job per question, OD-1109-QUOTA), 2000 per day (OD-1109-DAILYCAP), 2 documents per background job, up to 31 documents stored by one live prompt, and 30 prompts per hour and 180 per day per client (owner decisions OD-1031-PROMPTLIM and OD-1031-CEIL31)). A kill switch, `VERA_AUTOACQ_DISABLED=1`, turns acquisition off.
5. **Corpus digest.** `GET /corpus-summary` returns a model-written digest of the stored collection. A claim-level checker accepts only statements that match recorded facts and approved fact phrases; coverage figures are computed by code, not by the model. The latest digest is stored in the database so it survives a restart (`config/request_trace.json` `digest_store`; offline-tested, live behaviour unverified).
6. **Reading list fallback.** Otherwise the response is a list of published documents that may be relevant, with links, from the search providers above. VERA-DAR has not read those documents, and the response says so.

Answers from acquired documents carry a notice. When the collection is insufficient for a question, VERA-DAR searches for and reads more open-access full texts in the same request before answering; with automatic search off it returns the reading list and says that search is off.

## Memory and what is stored

**Live statistics (off by default).** When the owner enables live stats, one anonymous record is kept per answer (result type, counts, latency, time rounded to the hour; no question text or identifiers). While the flag is off, nothing changes.

Five questions, answered from the code of this candidate:

1. **What persists?** The evidence corpus: open-access full-text documents the operator selected or that automatic acquisition added (title, landing URL, licence, full-text chunks, provenance). **User memory is off**: no visitor profile and no conversation memory. The question is not part of the evidence corpus and the derived search query is not stored; the one exception is the owner-only request trace (see Privacy). `memory.store.enabled` is `false` in `config/ask-provider-chain.json`, and the owner review routes (`/memory/...`) return 503.
2. **When is it written?** After a question is accepted, when a fetched open-access document passes the licence, content, injection and relevance checks. This can happen inside the request (inline acquisition) or in a queued background job, bounded by `config/auto_acquire.json` (120 jobs/hour, one job per question, OD-1109-QUOTA; 2000/day, OD-1109-DAILYCAP; 2 documents per background job, up to 31 per live prompt, 30 prompts/hour and 180/day per client, OD-1031-PROMPTLIM and OD-1031-CEIL31; kill switch `VERA_AUTOACQ_DISABLED=1`). Documents with too few relevant passages are used for that one answer only and not saved.
3. **Where does it live?** In Postgres (documents, chunks and provenance), written through the app's write account.
4. **How is it retrieved?** Stored documents are loaded into an in-process index (BM25 passage search, `vera/fulldoc_corpus.py`, `vera/dar_corpus.py`); the acquired set is refreshed in the background, at most every 300 s. *Superseded in part (2026-11-09): there is no cap on stored documents, and a refresh with only newer rows appends to a fork of the serving index; with hybrid retrieval on, an embedding-similarity list is fused with BM25 (see the Update paragraph near the top).* Retrieved passages go through admission and the claim check before they can support an answer. (The disabled user-memory feature, if enabled, would recall only owner-confirmed rows by term matching, with a 30-day TTL and 14-day half-life.)
5. **When is it removed?** No removal mechanism for corpus documents was found in the application code or the repository's SQL (a search for delete, truncate and expiry paths outside tests, as of 2026-10-22; the corpus store is written insert-only, `vera/dar_store.py`). Documents are kept until the operator removes them by hand in the database, and the public deployment is planned to run through 2026-11-30 (owner decision OD-1027, 2026-10-27; this supersedes the earlier 2026-10-31 end date). Only the disabled user-memory feature has an expiry (TTL and owner rejection).

Other settings: discovery notes are written only when the `L2` layer is enabled (the shipped contract lists `L0` only), and corpus admission of abstract-level sources is off (`corpus.enabled` is `false`).

## Privacy and data handling

*Superseded 2026-11-06: the full text is on About only, the Ask page shows the short notice.* The data-use disclosure is built from the live configuration in `vera/disclosure.py`. With the shipped configuration its closing text says that the question is sent to third-party AI and search services, that VERA-DAR does not save the question or information identifying the user, and that its collection may grow with open-access full text found while searching. When full-document answering (enabled in the shipped configuration, but in effect only when a corpus source is configured; see [Default behaviour](docs/api.md#default-behaviour)) answers from the collection, the question, the selected passages with their titles and links, and draft answer sentences are sent to third-party AI services. When the Current-reporting lane is enabled (it is, in config, as of 2026-11-04) or the Official lane is (still off), the following applies. Search terms derived from your question may also be sent to GDELT (a news index); Hacker News search is not used. VERA-DAR may read public web pages from vendors and news outlets to answer; these pages are used only for your answer, and page text is not saved. Pages read for one answer are not licence-cleared or stored. GDELT is credited: [GDELT](https://www.gdeltproject.org/).

What the code shows:

- Acquisition runs inside the request (inline, whenever the collection is insufficient) and can also queue a background job. Terms from the question go to Groq (safety check, answering, claim checking) and to the search services: DuckDuckGo, OpenAlex, Europe PMC, arXiv and the Wikipedia API.
- Stored in the corpus: acquired open-access documents (title, landing URL, licence, full-text chunks, provenance). The derived search query is not stored. The question is held in memory for a queued job (maximum age 600 s).
- Request trace (`config/request_trace.json`): per request, an event log of closed reason codes, ids, scores and counts is written to the database (database sink on since 2026-11-04, after the owner applied migration 015; owner-reported, not seen by agents). The trace key allowlist (Deny All) drops any detail key not listed, and event details never hold question text. The question text is kept in the requests table, owner-only, and the owner purges it after 30 days with an owner-run script (`work/PERF-MISS-1104/trace/purge_trace.sh`; purging is a manual step today). An automatic 30-day purge is available but off by default (2026-11-05): `retention_purge.enabled` in `config/request_trace.json` (default `false`; needs `db_sink.enabled`) makes `vera/retention_purge.py` call `vera_vjay.purge_expired_trace()` once a day, started at API boot when on. Turning it on requires migration 018 (`db/migrations/pending/018-DRAFT-trace-purge-erasure.sql.draft`, a draft, not applied; owner-run, with rollback) and then the flag. *Superseded (2026-11-08, DOCS-1108): the flag is now true in config (commit 6ef1287, OD-1105-PURGE-ENABLE) and migration 018 was applied by the owner on 2026-11-08 (owner-run apply; not independently checked against the database), so the automatic purge is enabled; migration status is owned by `db/README.md`.* The request id is shown to the owner only (response header, logs, database), never in the interface. The question is not written to host logs (`log_sink.include_question=false`). The page disclosure text built in `vera/disclosure.py` may still say the question is not saved; reconciling it is an open item.
- Corpus digest state is stored in the database (see How it works, step 5).
- Topic tags (available, off by default): `vera/topic_tagging.py` can tag stored passages and documents with topics in one background worker. `enabled` in `config/topic_tagging.json` is `false`; it needs migration 017 (draft in `db/migrations/pending/`, not applied; owner step) and the owner-confirmed limits (`limits_confirmed`). It stores topic labels for stored corpus text only, not question text. The digest reads the tags only if `topics_source` is set to `table_if_present` (default: model clusters).
- Database-backed lists (available, off by default): `config/list_tables.json` `read_from_db` is `false`; the code reads the seed config files. Turning it on needs migration 016 (staged in `work/LISTS-TO-DB-1104/staged/`, not in `db/`, not applied; owner step). On any database failure the loader falls back to the seed file. Wired so far: the trace key allowlist and the digest numeric words.
- Request caps and rate-limit counters are held in process memory, and the DuckDuckGo query cache was described as disabled in the demonstration configuration (*2026-11-10: `config/vera_eval_run.json` now sets an in-process `memory_cache_ttl_s`, 900 s, and `config/ddg_reduce.json` longer normalised-cache settings; the disk cache path is unset; unverified live*); see [API and data use](docs/api.md).
- Provider retention, and the hosting platform's standard access logs (client IP, path, status), are outside VERA-DAR's control.

Records written by earlier configurations are not erased by this configuration.

## Limitations

- Full-document answers need a configured corpus source; the collection is small, so most questions get a reading list or a decline.
- Claim checking is done by a language model and can be wrong.
- Thresholds are placeholders pending calibration on live data.
- Licence labels come from indexing services and publisher XML and are not verified with rights holders. For listed results whose full text was not acquired, the label reads "Index metadata: <id>; article licence not verified" only when the licence check allows the record and the index declares a licence (for example CC0 for the index record); without a declared licence it reads "article licence not verified (link only)", and held or rejected records keep their hold or reject label. None of these is a licence for the article.
- The safety gate's layer 2 and the off-topic category accuracy are uncalibrated; the six-document round target and the lane limits are owner-declared or placeholder values.
- The request trace purge is manual (owner-run) as shipped, so the 30-day retention is not automatic. *Updated 2026-11-05:* an automatic daily purge exists but is off (`retention_purge.enabled=false`) and needs migration 018 (draft, not applied); until the owner applies it and enables the flag, the manual purge is the only purge. *Superseded in part 2026-11-08 (DOCS-1108): `config/request_trace.json` now has `retention_purge.enabled` true (commit 6ef1287, OD-1105-PURGE-ENABLE), and migration 018 was applied by the owner on 2026-11-08 (owner-run apply; not independently checked against the database), so the automatic purge is enabled; status is owned by `db/README.md`.*
- Live search and landing lookups in `/ask` run in parallel, one in-flight request per host (redirect hops included), and honour a site's robots.txt Crawl-delay (a malformed value skips the host). This is on and offline-tested only; not validated live.
- Comparative superiority over frontier models is unproven.
- Acquisition rounds, the news lane, the request trace and the corpus digest are offline-tested; they are not live-validated. Discovery-to-answer acquisition is offline-tested; it is not live-validated in production. Other live behaviour is untested (assumed) in this document; the free-tier host can be slow on first request.
- Known gaps in the acquisition fallback path: its fetch step does not yet reject a URL with a port or userinfo when no redirect chain is set (the arXiv licence gate does reject them); an unsigned evidence marker remains an open recorded residual risk (RR-1); and a missing or unparseable corpus timestamp is repaired in memory only unless the app has write access, so the repair is not persisted without a grant.
- The background acquisition queue is best effort and in memory; queued jobs are lost on restart.
- No removal mechanism exists for stored corpus documents (see Memory, answer 5).
